1손잡이는 셋입니다

아티클이 첫 문단에서 세 가지로 못박습니다.

“many applications using Claude Platform can cut cost without giving up performance with three fixes: maximize the prompt cache hit rate, remove anti-patterns from your prompts when upgrading to frontier Claude models, and calibrate effort to the task”
  • 캐시 — 앞부분이 그대로면 다시 계산하지 않습니다. 값이 가장 크게 움직이는 자리입니다.
  • 지시문 — 옛 모델의 약점을 메우려 넣은 주문이 지금은 값이 됩니다.
  • effort — 일의 무게에 맞춥니다. 높다고 늘 좋지 않습니다.
셋은 서로 곱해집니다. 캐시를 고친 다음 지시문을 걷어내고, 그 위에서 effort 를 재는 순서가 아티클의 순서입니다.

2복사해서 쓰는 요청 뼈대

요청을 이 순서로 짜면 앞부분이 매번 같아져 캐시가 걸립니다. 그대로 복사해 내 값만 채우세요.

{
  "tools":    [ ... ],   // 전부 앞에 선언 · 거의 안 쓰는 것에만 defer_loading
  "system":   "역할 · 규칙 · 용어집 · 예시 — 안 바뀌는 것만",

  // ─── 캐시 끊는 자리(cache breakpoint) · 여기까지가 캐시 ───

  "messages": [ "지금 시각 · 요청 ID · 사용자 이름 — 바뀌는 값은 전부 여기",
                "(이번 질문)" ]
}
  • 바뀌는 값을 위로 올리지 않습니다. 시각·요청 ID 가 시스템 프롬프트에 있으면 앞부분이 매번 달라져 캐시가 통째로 깨집니다 — 바이트 단위로 같아야 읽습니다.
  • 도구는 전부 앞에 선언합니다. 거의 안 쓰는 것에만 defer_loading 을 달면, 그 도구만 캐시 앞부분에서 빠져 대화 쪽에 붙습니다.
  • effort·모델은 대화 도중에 바꾸지 않습니다. 이 값도 앞부분에 실립니다 — 바꿔야 하면 어차피 캐시가 깨지는 순간(대화 압축 같은 때)에 같이 바꾸세요.
  • 대화가 길어지면 끊는 자리를 뒤로 옮깁니다. 자동 캐싱을 켜면 마지막 캐시 가능한 블록에 알아서 붙습니다.
  • 캐시는 5분이면 사라집니다 — 요청이 «시작된» 때부터 셉니다. 도구 호출이나 서브에이전트가 그보다 오래 걸려 부모 캐시가 만료되면 앞부분에 1시간짜리를 겁니다.
  • 세션을 열 때 한 번 데웁니다 — max_tokens: 0 에 끊는 자리를 명시하고, 실제 트래픽과 같은 effort 설정으로 보냅니다.

3찾아서 바꿀 문장 여섯 쌍

내 프롬프트·스킬·도구 설명에서 왼쪽을 찾아 오른쪽으로 바꾸면 끝입니다. 지우기만 해도 되는 줄은 그렇게 적어 뒀습니다.

찾을 말그 자리에 넣을 말
“두 번 확인해”
“답하기 전에 검증해”
검증 의식
지웁니다. 대신 「근거를 못 찾은 항목은 «못 찾음»이라고 적어.」
곧이곧대로 지켜서 같은 조회를 두 번 합니다
“최대한 꼼꼼히”
“CRITICAL: YOU MUST ALWAYS…”
강조 부스터
지웁니다. 대신 원하는 결과를 적습니다 — 「답은 세 문단 안에.」
말이 길어지고 도구를 더 부릅니다
“스크래치패드에 단계별로 생각해”
절차 강제
지웁니다. 모델이 이미 하는 일 위에 한 겹 더 쌓는 것입니다.
옛 모델 실수를 고치려 넣은 예시 묶음
낡은 예시
출력 «형식» 예시 한 개만 남기고 나머지는 지웁니다.
긴 추론을 흉내 내게 가르칩니다
“정책 안이면 환불”
+ “승인 없이 환불 금지”
어긋난 규칙
우선순위를 적습니다 — 「둘이 부딪히면 앞 규칙을 따르고, 뒤 규칙을 못 지킨 이유를 한 줄 적어.」
최신 모델은 둘 다 지키려다 멈춥니다
손으로 잡아 둔 thinking budget 같은 설정
낡은 설정
지웁니다. 기본값에 맡깁니다 — 새 모델에서는 요청이 거부되기도 합니다.
여섯 개를 하나씩 심어 재 봤더니 — “Running /claude-api prompt-audit removed the anti-patterns, decreasing costs by 14.6% and increasing accuracy by 5.3% on average”
정확도가 «오른» 이유가 재밌습니다. 어긋난 환불 규칙 때문에 줘야 할 환불 네 건을 붙들고 있었고, 손으로 만든 스크래치패드가 모델의 내장 사고와 부딪혀 도구 호출을 생각 안에 적고 실행하지 않은 티켓이 세 건이었습니다.

4복사해서 쓰는 effort 규칙

effort 는 «얼마나 열심히 할지»입니다. 아래를 팀 문서에 그대로 붙여 두고, 일을 시작할 때 한 줄을 고르세요.

[ effort 규칙 ]
답이 이미 준 자료 안에 있다        →  low
찾을 곳이 여러 군데다              →  medium
가설을 세우고 확인해야 한다        →  high
답이 있는지조차 모른다             →  max

바꾸는 자리   : 대화 도중이 아니라 «새 대화를 열 때»
되돌리는 자리 : 한 칸 올려도 답이 안 바뀌면 도로 내린다
고르는 모델   : 약한 모델을 세게 굴리기보다 «센 모델을 낮은 effort 로»
Claude Fable 5 · 어려운 코딩 50문제한 문제 값점수
low$5.3511.5%
max$19.0030.9%

점수는 약 2.7배(+19점) 오르는데 값은 약 3.5배입니다 — “raises the score about 2.7x (+19 points) for about 3.5x the cost”

  • 높다고 좋은 게 아닙니다. 필요보다 오래 재면 값과 시간만 늘고 답이 나빠질 수 있습니다. 「Deliberation only helps while there's still evidence to find.」
  • 낮다고 싼 것도 아닙니다. 증거가 모자란 채로 멈춥니다 — 「The answer looks finished, but it's built on partial information.」
